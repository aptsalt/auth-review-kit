Identity Modernization, Release 3

The complete login and session architecture — OAuth2, PKCE, DPoP, step-up, and logout — laid over the code that actually implements it. Every claim carries an evidence marker: verified partial needs evidence. Source: 04-identity-r3-architecture-explainer.md.

The mental model

Atlas UI never talks to the vault directly for security decisions. Password check, biometric check, token issuance, DPoP validation, fraud scoring — all of it goes through Sentinel. Atlas BFF and Gateway deal only in business data — but Gateway still enforces token and DPoP validity on every single call.

Architect note — the two-session split

There are two sessions here, and conflating them produces most bad findings: the security session owned by Sentinel (tokens, grants, token cache), and the application session owned by Atlas BFF (/initAppSession, account summary). They are tied together only by the IDP_Correlation_ID BFF stores. Ending one does not end the other — which is exactly why §6.3 makes the UI call both and clear locally regardless.

§2.1

OAuth2 authorization code flow

Think of it as a hotel key card. You prove who you are at the front desk (/authorize). The desk doesn't hand you the key card — it hands you a temporary claim ticket (the authorization code). You take that to the back office (/token) and trade it for the real key card (access token) plus a spare key request slip (refresh token). The key card opens your room until it expires; the slip gets you a new one without checking in again.

§2.2

PKCE — the acronym the doc never spells out

The doc says Sentinel "validates code verifier & returns access & refresh tokens." That is PKCE — Proof Key for Code Exchange. It exists because a browser app is a public client: it has no secret it can hide. Without protection, an attacker who intercepts the authorization code (malicious redirect, OS-level URL hijack on mobile) could trade it for tokens themselves.

The boundary most people get wrong

PKCE protects the code exchange. It does not protect the integrity of the /authorize request parameters. That is why the alg:none request object below is still a real finding even though PKCE is implemented correctly. Being able to draw that line is what separates a reviewer from an operator.

In our repos — atlas-ui PKCE is genuinely implemented — generateCodeVerifier() (96-char base64url) and generateCodeChallenge() (SHA-256) at auth.service.ts#L892-L910; codes cleared on logout via clearAllPkceCodes (#L811-L813).
Real finding — request object integrity The /authorize request object is sent as an alg:none unsigned JWT (auth.utils.service.ts#L21-L24) and Sentinel is configured to accept it — request_object_signing_alg: none for spapublicclient/spamobileclient in clients.j2#L25. Request parameters aren't integrity-protected. The newer idp_v2 template already uses RS256 — a config drift worth flagging.
Finding heuristic Flag any repo that builds an authorization request without a challenge/verifier pair, reuses a verifier across sessions, or logs the verifier anywhere (Splunk, EventBus). Each defeats PKCE entirely.
§2.3

DPoP — Demonstration of Proof-of-Possession

The problem: a plain OAuth access token is a bearer token — whoever holds it can spend it, like cash. If it leaks via XSS, a log, or a MITM, the attacker replays it from anywhere until it expires. The fix: DPoP staples the token to a specific browser's private key — a boarding pass only your passport can validate. RFC 9449

Where it shows up in findings territory

1. HttpAdapter classes in HUB repos must attach a freshly generated proof per call, never a cached one. 2. The 60-second window is enforced in two places independently — Sentinel and Gateway — so divergence between them is itself the finding. 3. The UI must clear the DPoP key pair on logout and on any token-alteration error; a forgotten path leaves a stale key reusable after logout.

In our repos — atlas-ui

The doc's claim that Sentinel and Gateway enforce it independently cannot be verified here: treat any replay-window finding as NEEDS-EVIDENCE. Open question worth chasing: is there a jti replay cache at all, or only an iat check?

§3

Login — UC.3-1.1.1

Simple version: customer enters card number or User ID + password (or biometric); the app proves this to Sentinel, gets tokens, then tells Atlas BFF "start my session," and BFF loads account data.

  1. Atlas UI collects the credential and encrypts it client-side before sending to AuthKit MFE, which forwards to Sentinel's /auth.
  2. Sentinel calls CredentialAuthentication to validate the password against Directory.
    • If login is by User ID, Sentinel calls Credential Management Service to resolve the card number and transaction CIF ID, tagged x_proxy_cardnumber / x_transaction_cifID.
  3. Sentinel publishes a password validation event to EventBus — this drives the §4 prefetch.
  4. Sentinel returns an authorization code + callback URL to AuthKit MFE.
  5. Atlas SPA calls /authorize with that code; Sentinel validates the PKCE verifier and returns access + refresh tokens.
  6. Sentinel pushes sign-in success/failure/attempt events — including RiskEngine fraud results from the risk vendors — to the SignIn event topic.
  7. Atlas UI generates the DPoP key pair and signs every call from here on.
  8. Atlas UI calls /initAppSession on Atlas BFF to start the application session. BFF stores IDP_Correlation_ID, retrieves the credential record from Directory, loads the account summary (GridCache if prefetched), and writes AuthEvents.App.LoginSuccess/LoginFailure.

§4

Remember Me & login optimization

Remember Me: a device token says "this browser logged in as user X before," so Atlas pre-fills the username field. R3 supports two formats — legacy and the new Sentinel format — and a legacy token is silently migrated without the customer noticing.

Login optimization: don't make the customer wait for account data after authenticating — start fetching the moment the password is confirmed, in parallel with the rest of the auth flow.

Architect note — a pre-authorization trust decision

Data is prefetched after password validation but before the OAuth flow, fraud scoring and any step-up complete. That is a deliberate latency-for-risk trade, made safe by three choices: it caches profile data only, credit-card logins are excluded, and the cache is only read by BFF after full login. Any change that widens what is prefetched, or lets the cache be read earlier, converts a performance optimization into an authorization bypass. Raising that is the architect's job.

In our repos Remember-Me is implemented, but only the new path is clearly present — remember-me-token.adapter.ts; saved-card.service.ts#L22 carries remembermeToken.
Missing / verify The legacy→new silent migration and the 64-byte hashed-card alias are Directory / Credential-Management-Service concerns — not in the client repos.

NativeMFA is IBM the IdP platform's built-in biometric flow. Instead of Northwind storing its own biometric token format, the phone's fingerprint/FaceID unlocks a stored OAuth refresh token, which is then exchanged like any other — no proprietary validation logic. This is why NativeMFA registration is implemented internally as a High-Risk Transaction (see §7).

Architect note — local unlock vs remote factor

The strategic move is replacing a proprietary secret store with a standard token lifecycle. The biometric is not a factor being transmitted — it is a local unlock gesture for a credential that already exists on the device. That is the same distinction underpinning FIDO2/WebAuthn and passkeys, and it is the correct answer when someone asks "is the fingerprint sent to the bank?" — it is not.

§6

Session, keep-alive, timeout, logout

The section most relevant to reliability and session findings. Three intertwined sub-flows plus one important edge case.

6.1

Keeping a session alive

  • Before every API call the UI asks: is the access token expired, or less than 15 seconds from expiring? If so it refreshes first — avoiding a race where the token dies mid-request.
  • Gateway exposes a dedicated keep-alive API to extend the session without a full token refresh.
  • On "Stay Signed In", the UI refreshes and swaps tokens in-place.
In our repos The 15-second buffer is real — TOKEN_EXPIRATION_BUFFER_MS = 15000 (auth.constants.ts#L123), consumed by isTokensValid (auth.service.ts#L345-L355).

The rule that matters

"Clear locally no matter what the server call outcome is." A token or DPoP key left behind after a failed logout is treated in this architecture as a real risk, not an edge case.

Naming drift Some sequence diagrams reference session_logout replacing unified_logout. Check which endpoint name is current in a given repo before concluding logout is broken.
6.4

Security-error forced cleanup

If Sentinel or Gateway detect a token alteration (tampered token or DPoP proof), the UI must: remove DPoP keys → clear all tokens + session storage → show the session-expiry page. And for the Gateway error case specifically, call logout on Sentinel first — an extra step not required for the Sentinel-error case.

Decision — the ordering detail that's easy to get wrong

In our repos The cleanup exists as a separate method, cleanupTokensAndTimeouts() (auth.service.ts#L781-L812) — clears sessionStorage token keys, cookies, permanent storage, the DPoP key (cleanupStoredDpopKeyAndState, #L815-L850) and PKCE codes.
High-value check — verifiable today logout() (#L762-L774) only calls isamClient.logout() and re-throws on error; its finally just resets logoutInProgress. The server call and the local cleanup are decoupled, orchestrated by LogoutService. If LogoutService only cleans up on the success path, tokens and DPoP keys survive a failed logout — a direct contradiction of §6.3/§6.4 and a strong candidate finding. Also verify the Gateway-error ordering.
§7

DPoP-protected calls & high-risk step-up

Simple version: every API call is DPoP-signed. For sensitive actions — adding a payee, transferring money, PIN reset, changing alert delivery — the system checks fraud risk in real time and may demand OTP/step-up before letting it through.

  1. Atlas UI attaches a DPoP proof to every request.
  2. Gateway validates the proof for every transaction, not just login: checks iat in the same 60s window independently, caches the PDP result, and parks the pending payload in a Transaction Cache (60-min TTL).
  3. If the transaction is high-risk (fixed list of ~25 types), Sentinel calls RiskEngine with the transaction ID and custom facts.
    • RiskEngine returns "Review" → Sentinel fails the transaction outright. No retry, no soft-decline. Remember this when triaging "why was my legit transaction blocked".
    • If the RSA analyze call times out → also hard-fail. But if only the notify call or an EventBus publish fails → log and continue. The asymmetry is intentional.
  4. Anti-replay / session binding: compare the sub from TXSUB in the access token against the sub stored in the transaction cache. Mismatch → invalidate the token, delete the cache entry, invalidate all login grants on web AND mobile, return a security error.

What this actually is

Parking the payload and re-binding it to the user after OTP is hand-rolled dynamic linking — the PSD2 SCA requirement that authentication be cryptographically tied to that specific transaction. Note Northwind does step-up as a transaction property, not as a token property (acr). Know both models.

In our repos — sentinel-config TXSUB claim handling: saveRsubClaims() (NativeMFA_oauth_AccessPolicy.js#L66), mapRsubAttrs() (Hub_pre_token_generation.js#L53), RSUB_LIFETIME = 3610s.
Gaps — high severity if missing
  • The sub compare-and-invalidate block could not be located — only TXSUB save/map was found. A missing or web-only comparison is exactly the high-severity finding §7 describes. Trace AccessPolicyFunctions.js before concluding it's implemented.
  • Transaction Cache and Gateway PDP caching live in Gateway config — NEEDS-EVIDENCE.
  • Confirm the asymmetric fail behaviour in the RiskEngine access policy before "fixing" any fail-open/closed finding.

§9

User ID conversion

Most customers log in with a card number. This lets an eligible customer create a User ID and convert their credential from card-number-based to User-ID-based — a security improvement (card numbers are guessable and enumerable) and an the prudential regulator regulatory requirement.

  1. Eligibility file loaded via the eligibility feed → the feed loader → sets enrollment flags in Directory.
  2. At login, Atlas UI calls the eligibility API — if eligible and not previously dismissed, shows the prompt.
  3. Conversion is itself a High-Risk Transaction — it goes through the §7 OTP step-up before being allowed.
  4. On conversion: Credential Mgmt validates the ID isn't blacklisted; the Remember-Me token switches to GUID lookup and drops credential type; the old card-number biometric mapping is preserved by matching a 64-byte hashed-card alias in Directory; saved payees migrate via SecureFormMigrationService; and a backup branch in Directory is created first so the whole thing can roll back.
Patterns worth stealing

Identity continuity across a credential change (the hashed-card alias keeps biometric registration alive), and a reversible checkpoint before any identity migration (the Directory backup branch). Both belong in any migration you design.

Mostly not in our repos Only the PWD_BLACKLIST error codes surface client-side (error.adapter.ts#L225-L226). SecureFormMigrationService, the Client Credential Orchestration API, the GUID alias rewrite and the Directory rollback are backend services — treat the whole §9 flow as NEEDS-EVIDENCE and don't raise code findings against it from these repos alone.
§10

POA, password reset, registration

Mostly Release 3.2, small-business-focused enhancements layered onto existing self-serve registration and reset flows.

  • P2A role auto-linking: existing role players automatically get the POA-related "P2A" role, so they receive OTP through their own delivery method instead of needing manual re-setup.
  • POA registration with existing credentials: a POA user who already has Atlas credentials from another card extends access to a new business card without a second login.
  • POA password reset: reset gets POA-aware checks — reject where the card assignment creates ambiguity, and send confirmations to the business owner / Authorized Signatory, not just the POA user.
  • Registration reuse: reuse the existing user-ID credential from the credit card rather than forcing a brand-new one.
  • Admin console: a new credential-change history view, sourced from the EventBus events described throughout this document.

§12

How to use this when reviewing findings

  1. Finding mentions token / session / DPoP → identify which of the lifecycles it touches using §2.4. Storage and cleanup rules differ per row.
  2. Finding about replay or "old request accepted" → check the 60-second iat window (§2.3), and confirm whether it's enforced at Sentinel, Gateway or both. Independent implementations drift.
  3. Finding about logout not clearing state → §6.3/§6.4. The rule is "clear locally no matter what." Clearing only on success is a direct contradiction of the requirement.
  4. Finding about high-risk transactions failing oddly → check §7's asymmetric failure handling before assuming it's a bug.
  5. Finding in WealthDesk session handling → its timeout values are overridden and must not regress from CIAM changes (§6.2).

★

The one paragraph — say it from memory

A customer hits the Atlas SPA, which federates in the AuthKit MFE micro-frontend. The credential is encrypted client-side and validated by Sentinel against the Directory. Sentinel runs a standard OAuth 2.0 authorization-code flow with PKCE — the SPA is a public client, so it commits to a hashed challenge up front and redeems the code with the original verifier. The tokens that come back are not bearer tokens: they are DPoP-bound to a key pair whose private half never leaves the device's secure keystore, so every call carries a freshly signed proof with htm/htu/iat/jti/ath, checked against a 60-second replay window independently by both Sentinel and the Gateway gateway. The access token lives in memory only, the refresh token in sessionStorage, and the UI refreshes 15 seconds before expiry. A second, separate application session lives in Atlas BFF, tied back by IDP_Correlation_ID and warmed by an EventBus-driven prefetch that starts the instant the password validates. Sensitive actions escalate into a high-risk-transaction step-up: Gateway parks the payload in a 60-minute transaction cache, RiskEngine scores risk through the risk vendors, and after OTP the system re-binds the transaction by comparing the token's TXSUB against the cached sub — a mismatch nukes the token, the cached transaction, and every login grant on web and mobile. Logout is triple-sided and the local clear is unconditional by design. Everything is published to EventBus and consumed by the datamart, Warehouse and Splunk.
