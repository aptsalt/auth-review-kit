From review findings to a self-healing SDLC

Fix the class, not the instance

28 repos of findings is not the asset. The patterns across them are. A defect appearing in nine repos is not nine developers making nine mistakes — it is the delivery process permitting it nine times. That distinction is what turns an audit into a funded programme.

01

The pivot

Findings list

Arrives as N problems belonging to N teams. Reads as a scoreboard. Teams defend, argue scope, and absorb the work as unplanned cost. It ages out in a sprint and nobody re-runs it. Best case, some bugs get fixed. The next repo ships the same defect.

Pattern list

Arrives as a handful of classes, each present in many repos, each with a named control that would have prevented it. Belongs to the platform, not to any team. Nobody is blamed. The fix is structural, so it holds for repo 29 without anyone reviewing it.

One is a code review. The other is a process finding — and process findings are the only kind that get funded.

You also hold something almost nobody proposing an SDLC change has: telemetry evidence for which defect classes actually cost production. That converts "we should add guardrails" into "these three classes caused real incidents in the last 30 days, and here is the specific control that would have caught each one." That is an argument that survives a steering committee.

The sentence to open with

"I reviewed 28 repositories and cross-checked every finding against 30 days of production telemetry. I am not here with a list of bugs for your teams. I am here with six defect classes our delivery process currently allows, ranked by what production is already paying for them."

03

The intervention ladder

For every class, you can intervene at four heights. Most organisations reach for the second rung and wonder why nothing improves. Climb as high as the class allows.

1 · detect
Report it

A scan produces a list. Zero friction, zero enforcement — and zero change, because a report nobody is accountable for is a report nobody reads. Useful only as a baseline measurement.

2 · warn
Comment on the PR

Non-blocking annotation at the moment of change. Better, because the feedback lands where the decision is made. Decays: warnings that are routinely ignored train people to ignore warnings.

3 · block
Fail the build

Now it holds. Costs goodwill if the rule is noisy, so a blocking rule must be near-zero false positive and have a documented, quick escape hatch. Earn this rung with data, don't assume it.

4 · prevent
Make it unbuildable

The rung that actually ends a defect class. Not a rule that catches a missing timeout — a client that cannot be constructed without one. Not a scan for raw JWT decoding — a library where the only available method verifies. Nothing to remember, nothing to enforce, no false positives, and it works for every repo written after it, forever.

A rule tells people not to make the mistake. A design means the mistake has no expression.

Prevention is not always reachable — you cannot design away a fail-open policy decision. When you can't reach rung 4, land on 3 for classes production has observed, and 2 for the rest. Say which rung you are proposing and why; that specificity is what makes it a plan rather than an aspiration.

04

The agentic loop

Seven stages. The agent does the expensive reading and drafting; a human owns every gate where consequence enters the system. The loop only closes when telemetry confirms the signal actually dropped — without that last arrow it is not a loop, it is a pipeline that generates work.

02 · Correlate

The stage everything else depends on. Entity-to-repo mapping must be explicit, and low-confidence matches must stop here rather than proceed. A confidently wrong correlation sends the agent to fix the wrong file — and one of those in front of a team costs more trust than ten good PRs earn.

03 · Triage gate

Cheap, and it protects everything downstream. A human spends thirty seconds confirming the correlation is plausible. Skipping this to look more autonomous is the most common way these systems fail.

05 · Draft PR

Failing test first. The test is the deliverable; the fix is the easy part. A PR that only changes code asks a reviewer to trust the agent's reasoning. A PR with a test that fails before and passes after asks them to trust the test — which is a thing they can actually verify in seconds.

07 · Guardrail

Where self-healing actually happens. Fixing the instance is a patch. Adding the control that makes the class unrepresentable is the healing. If stage 07 is skipped, the loop generates an endless supply of stage 05.

The closing arrow

After the merge reaches production, the agent re-queries telemetry for the original signal. Signal gone → the story closes with evidence. Signal unchanged → the fix was wrong, and the ticket reopens automatically with that fact attached. This is the single most valuable part of the design and the part everyone leaves out — it is what stops the system confidently generating plausible fixes that change nothing.

05

Maturity — and where to stop

Do not propose the top of this ladder. Propose L1, demonstrate it, and let the organisation pull you upward. Every level is independently valuable, which means every level is a place you can credibly stop.

L0
Manual

A human notices a problem, hunts the code, writes the ticket, writes the fix.

today
L1
Enrichment

A problem fires; the agent attaches code context, the owning repo, recent changes and prior related findings. No code is written. Pure time saved, zero risk.

start here — earns trust with nothing at stake
L2
Authored story

The agent writes the ticket: evidence, blast radius, suspected root cause, affected users. A human accepts or rejects.

low risk, visible value
L3
Draft PR with a test

The agent opens a draft PR: failing test, then the fix. Never auto-merged, never marked ready without a human.

the honest target for most teams
L4
Guardrail authoring

On a recurring class, the agent proposes the lint rule, architecture test or scaffold change that prevents recurrence — as its own reviewed PR.

the real prize. stop here in a regulated estate.
L5
Autonomous merge

The agent merges without human approval, inside a narrow allowlist, with automatic rollback.

not in a bank. not on auth code. don't propose it.
Say this out loud, early

"There is no stage in this design where an agent merges code without a named human approving it." You will be asked. Answering it before you are asked is what gets you past risk and audit — and volunteering your own ceiling is what makes the rest of the proposal credible.

06

How this loses trust

Each of these has killed a real programme. Design against them from the start — and name them in the proposal, because the people who will approve this are already thinking them.

The confidently wrong PR

A subtly incorrect fix, delivered with conviction, wastes a senior engineer's afternoon. Two of those and the system is switched off. Mitigation: low confidence must produce a question, not a patch — and every PR carries its correlation verdict so a reviewer can calibrate before reading a line.

The noisy guardrail

A blocking rule with false positives gets disabled within two sprints, and the next proposed rule is refused on sight. Mitigation: ship every rule in warn mode, measure its false-positive rate on real history, and only promote to blocking with that number in hand.

Volume as a proxy for value

"The agent opened 60 PRs this month" is not a result — it may be a cost. Mitigation: measure merged-without-rework rate, defect classes closed, and repeat-incident rate. Never PR count.

Unclear accountability

When an agent-authored change breaks production, "the AI did it" is not an answer a bank accepts. Mitigation: the approving human is the author of record. The agent is a tool, exactly like an IDE refactor — say this in those words.

Correlation drift

Entity-to-repo mappings rot as services are renamed and split. Mitigation: unmapped entities are a tracked defect, and stale mappings fail the run loudly rather than silently mis-attributing.

Audit and change control

Regulated change management needs a traceable chain. Mitigation: every artifact links backwards — guardrail to PR to story to correlation to the original problem ID. Build that chain from day one; retrofitting it is painful and it is the first thing audit will ask for.

07

A 90-day sequence

Each phase is independently defensible, and each produces something you could stop at. That is deliberate — a proposal that only pays off at the end never gets started.

  1. Weeks 1–2 — Publish the pattern map. Turn your 28 repos of findings into the §02 table, ranked by prevalence × production corroboration. Circulate it with no ask attached. Let people react to the shape of the problem before you propose anything. Deliverable: one table, three pages of context.
  2. Weeks 3–4 — Land one guardrail, in warn mode. Pick the class that is highest prevalence and observed in production, and implement the highest rung on the ladder you can reach. Warn only. Measure the false-positive rate. Deliverable: a working control and a number.
  3. Weeks 5–6 — Promote it to blocking. With the false-positive number in hand, propose promotion. Publish the before/after count across the estate. Deliverable: the first defect class that is now structurally impossible.
  4. Weeks 7–9 — L1 enrichment. Wire the telemetry-to-code correlation so problems arrive pre-enriched with owning repo, code context and prior findings. No code generation at all. Deliverable: mean-time-to-context, before and after.
  5. Weeks 10–12 — L2/L3 on one team. One volunteer team, one repo, agent-authored stories and draft PRs with tests. Measure merged-without-rework. Deliverable: evidence for or against expanding — and be genuinely willing to report "against".
What makes this proposal different

Most SDLC pitches start at the tooling and argue toward the benefit. This one starts with evidence the organisation already owns — its own repos, its own telemetry — and argues toward the smallest control that would have prevented what already happened. Every step is measured, every step can be stopped, and the first two do not require anyone's permission to begin.
